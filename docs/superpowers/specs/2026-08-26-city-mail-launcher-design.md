# City Mail Launcher Design

## Goal

Replace the Gate C fixture's synthetic launcher with a private service that
consumes an immutable `gc.intake.start-authorized.v1` Agent Mail message,
starts one City `superpowers-build` workflow, and returns one exact
`gc.run.binding.v1` message to the bridge.

## Scope and authority

`city-mail-launcher` is a profile-gated Compose service. It has no published
port, Gitea URL, Gitea token, webhook secret, City HTTP API URL, issue-write
credential, or Mayor credential. Its only external capability is a private
Agent Mail registration held in a mode-0600 role file generated by bootstrap.

It mounts the same City, rig, and GC runtime paths used by the City supervisor
because `gc sling` writes the durable City workflow state. The launcher is
limited in code to `gc sling mayor ... --on superpowers-build`; it cannot
select another target or formula from a Mail message. It stores a local
authorization-to-run ledger so redelivery cannot create a second City run.

## Components

1. `Dockerfile.city` gains a minimal `launcher-runtime` target containing only
   `gc`, its required City helpers, shell/Python/JQ tooling, and the launcher
   entrypoint. It does not contain Codex configuration or authentication.
2. `scripts/city-mail-launcher.sh` loads its private role file, polls only the
   configured launcher identity's inbox, validates exact authorization fields,
   launches the fixed Mayor formula, sends the bridge a binding, and records
   completion before acknowledging the authorization message.
3. Bootstrap writes `state/city-mail-secrets/launcher.env` with the Mail HTTP
   bearer token, project key, launcher identity, and launcher registration
   token. The City supervisor remains unaware of this file.
4. `compose.yaml` adds the private launcher service and its durable ledger
   mount. The `gitea-mail-bridge` profile starts it alongside Agent Mail and
   the bridge.

## Data flow

```text
bridge -- authenticated start authorization --> launcher Mail inbox
launcher -- fixed gc sling mayor --on superpowers-build --> City workflow
launcher -- binding {authorization_id, pinned_base, run_id} --> bridge inbox
bridge -- persists ledger before acknowledgement --> durable intake record
```

The launcher's `run_id` is the `bead_id` returned by `gc sling --json`; the
binding copies the exact authorization ID, issue identity, plan, and immutable
`pinned_base`. A binding is sent only after `gc sling` reports success. The
launcher writes its own completed record before acknowledging the authorization
message. A failed launch or failed binding delivery remains unacknowledged for
redelivery; a repeated completed authorization resends the same binding without
launching again.

## Failure handling

- Invalid, expired, or malformed authorization messages are left unacknowledged
  and reported in launcher logs without leaking message credentials.
- `gc sling` failure does not send a binding and leaves the Mail message pending.
- Ledger persistence failure does not acknowledge the authorization.
- A duplicate authorization uses the persisted run ID and retries only the
  binding send.
- The launcher never reacts to arbitrary tracker Mail; it accepts only the
  exact authorization subject/type addressed to its own identity.

## Verification

Structural tests assert the authority matrix: no published launcher port; no
Gitea, Mayor, or City HTTP credential; a read-only launcher role file; only the
fixed `mayor`/`superpowers-build` command; and record-before-ack ordering.
Unit tests exercise authorization validation, duplicate handling, failed sling,
and failed ledger persistence. The live Gate D trace creates a disposable
issue, proves the real Mayor's public plan/IDD response, approves it, observes
the launcher binding and City workflow/run ID, and stores redacted Mail and
ledger evidence.
